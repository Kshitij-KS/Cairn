# log/ — where agents write, and where canon gets requested

This is the only part of cairn an agent may write to without a human. Three things live
here, and the difference between them is the difference between recording a fact and changing
what we believe.

| Folder | Holds | Written by | Review |
|---|---|---|---|
| `log/journal/` | **L0 observations**: gotchas, corrected assumptions, dead ends, real constraints | agents and contributors, automatically | none once `main` is protected and auto-merge is turned on; until then, the normal pull-request review |
| `log/proposals/` | requests to change `context/`, `decisions/` or `governance/` | agents and contributors | a human with the level's role promotes it |
| `log/CHANGELOG.md` | one generated line per commit | the CI bot | never edited by hand |

## journal/ — one fact, its consequence, and a link

File: `log/journal/YYYY-MM-DD-<slug>.md`. Frontmatter `title`, `type: gotcha` (or `note`),
`tags`. A one-paragraph summary, `## Observations` as `- [category] fact`, `## Relations` with
at least one link. **Eighty lines is the ceiling; fifteen is typical.** Do not write `author`,
`level` or `confidentiality` — the guard stamps them from the git identity, which is why
attribution here can be trusted.

Write one when a teammate would decide worse in a month without it. Do not write progress
narration, anything re-derivable from the diff or `git log`, a restatement of a doc already in
the repo, or something a recent note already says — the guard rejects an entry ≥85% similar to
one from the last 30 days, and the fix is to update the original.

## proposals/ — how anything above L0 changes

File: `log/proposals/PROPOSAL - <what>.md` (a dash, never a colon — `:` is illegal in Windows
filenames). The body must contain the **exact text** to be promoted, so the reviewer verifies
and pastes rather than reconstructing the author's reasoning:

```markdown
---
title: PROPOSAL - Move card payments to the new provider
type: proposal
status: open                     # open | promoted | rejected
target: context/tooling-stack.md # or: decisions/ADR-NNN (new)
tags: [proposal]
---

# PROPOSAL - Move card payments to the new provider

**Target:** `context/tooling-stack.md` (an example; your note will have its own sections)
**Change:** replace `- [decision] The payments provider is undecided` with
`- [decision] Card payments move to the new provider (trial 2026-09-20: 1.9% per charge, same failure rate)`
**Why:** two weeks of shadow traffic; results attached in PR #41.
**Conflicts with:** [[Tooling Stack]] currently records the payments provider as undecided.

## Observations
- [proposal] Card payments move to the new provider on trial evidence

## Relations
- relates_to [[Tooling Stack]]
```

## Promoting a proposal (humans)

Weekly, by whoever holds the role for that level (`governance/roles.json`; check with
`memory_guard.py explain --actor <handle>`):

1. **Find them.** `ls log/proposals/` or ask an agent to `search_notes` for `tag:proposal`.
2. **Verify** the claim against the source it names. No source → send it back.
3. **Check the level.** A project plan is L1 and needs that project's maintainer; company
   strategy is L2 and needs a steward; a rule change is L3 and needs an owner. You cannot
   promote above your own level — the guard will refuse the commit.
4. **Edit the target by hand**, in the note's own format: one-line observations, and add the
   relation so the graph connects. For a decision, create `decisions/ADR-NNN-*.md` from the
   template.
5. **Close the proposal:** set `status: promoted` (or `rejected` with one line why). Never
   delete it — the rejected ones are the most useful record you have.
6. **Commit** with a message starting `promote:` so it stands out in the changelog, e.g.
   `promote: tooling-stack — card payments move to the new provider (from log/proposals/…)`.
7. **Expect a cascade.** Promoting to L1/L2/L3 stamps `review_needed` on every note that depends on
   the one you changed (dependency edges, depth 1) and opens an issue listing them. Work that list down; it is bounded, and
   it is the mechanism that stops the rest of memory quietly contradicting the new decision.

## CHANGELOG.md

Generated by `.github/workflows/changelog.yml` on every push to `main`:
`YYYY-MM-DD HH:MM | level | author (agent) | N files (paths) | message`. The level column is
what lets you see at a glance whether a week was observation or strategy. For a richer view:

```bash
uv run -q --script scripts/memory_guard.py audit --since 30d          # who changed what, when
uv run -q --script scripts/memory_guard.py audit --since 90d --path context --verbose
```

## Observations
- [rule] `log/journal/` is for L0 observations and merges without review; `log/proposals/` is how anything above L0 changes ^109d92
- [rule] Proposals are titled `PROPOSAL - <what>` (dash, not colon: Windows filenames) and carry the exact replacement text ^77252f
- [rule] Promotion closes the proposal with `status: promoted` or `rejected`; nothing is deleted ^bb3a29
- [rule] Promoting to L1/L2/L3 cascades `review_needed` onto dependent notes — work that list down ^4e9d8f
- [rule] `CHANGELOG.md` is generated; hand edits are overwritten ^f371e8
- [constraint] Journal notes are capped at 80 lines and rejected at ≥85% similarity to a recent note ^61c9e6
